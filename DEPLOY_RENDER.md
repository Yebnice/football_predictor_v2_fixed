# Deploying: Render (API) + Streamlit Community Cloud (frontend)

Fact-checked against Render's own docs (render.com/docs/free and
render.com/docs/environment-variables, both current) before writing this —
here's what's actually true, not assumed.

## Why this split, not everything on one provider

Render CAN run both the FastAPI API and the Streamlit frontend as two
separate web services (there's a commented-out example of that in this
guide's alternative section below, if you'd rather do that). The reason to
split them instead:

- Render's free plan gives you 750 instance-hours/workspace/month, shared
  across free services in the workspace. Free services also spin down after
  15 minutes without inbound traffic and their local filesystem is ephemeral.
  citeturn285985search0
- Streamlit Community Cloud is free, unlimited for public apps, and is
  Streamlit's own purpose-built host — no spin-down tuning needed.
- `frontend/streamlit_app.py` runs the whole prediction engine **in-process**
  — it does not call the FastAPI API over HTTP. So the two services don't
  need to talk to each other at all; they only need to optionally share one
  Postgres database if you want one admin/VVIP tips board visible from both.

## Step 1 — Get a real, persistent Postgres database (do this first)

**This is not optional if you want data (admin accounts, VVIP tips) to
survive.** Confirmed from Render's own docs: free web services have no
persistent disk — local files are wiped on every spin-down. This app's
`app/db.py` will log a loud warning at startup if it detects this
misconfiguration on Render, but it won't stop you from launching without one
(unlike on a truly stateless host, where it refuses to start — Render *can*
legitimately use local SQLite on a paid plan with a Disk attached, so the
check can't be a hard block here).

Two free options that don't quietly delete your data:
- **Supabase** — free Postgres project. Pauses after 7 days with zero
  traffic; data survives, auto-resumes on next connection.
- **Neon** — free Postgres project. Auto-suspends after 5 min idle, resumes
  automatically on the next query — no manual "un-pause" step.

For Render, use an IPv4-reachable Postgres endpoint. **If you use Supabase, do
not copy the direct `db.<project-ref>.supabase.co:5432` connection on the free
plan**: Supabase documents that direct connections are IPv6-only there, while
Render is an IPv4-only network. Use the Supabase **shared Session pooler**
connection string from the Connect dialog instead (port 5432), or use another
IPv4-compatible database service. citeturn285985search4turn285985search6

The Supabase Session pooler will look broadly like:
```
postgresql://postgres.<PROJECT-REF>:PASSWORD@aws-<INDEX>-<REGION>.pooler.supabase.com:5432/postgres
```
**Copy the exact host, username and password from Supabase's Connect dialog**;
do not invent the pooler host from your region. citeturn285985search4

Keep that connection string — you'll paste it into both Render and (if you
want one shared admin/VVIP board) Streamlit Cloud's secrets.

*(Do NOT use Render's own free Postgres for this — confirmed it expires 30
days after creation, which defeats the point.)*

## Step 2 — Deploy the API to Render

1. Push this repo to GitHub if it isn't already there.
2. Render dashboard → **New** → **Blueprint** → connect your GitHub repo.
   Render reads `render.yaml` automatically and provisions the
   `football-predictor-api` service.
3. Render will pause and ask you to fill in the env vars marked
   `sync: false` in `render.yaml`:
   | Variable | What to put |
   |---|---|
   | `API_FOOTBALL_KEY` | optional; add it to enable API-Football in the provider chain |
   | `FOOTBALL_DATA_API_KEY` | optional; free registered token for football-data.org |
   | `DB_PATH` | the IPv4-compatible Postgres connection from Step 1 |
   | `CORS_ALLOWED_ORIGINS` | leave as `*` for initial testing, tighten in Step 4 |
   | `GROQ_API_KEY` | optional, for AI match explanations |

   `AUTH_JWT_SECRET` and `RNG_SALT` are auto-generated by the Render blueprint
   (`generateValue: true`). The application also blocks known placeholder
   secrets in `APP_ENV=production`.
4. Deploy. First request runs migrations against your Postgres DB automatically. If
   the database URL uses a Supabase direct `db.*.supabase.co` endpoint, the app
   now fails fast with an actionable IPv4/pooler message instead of producing
   the opaque `Network is unreachable` startup error.
5. **Verify it's actually working** — don't just trust a green checkmark:
   ```
   curl https://football-predictor-api.onrender.com/health
   ```
   Should return `{"status": "ok", ...}`. Then hit `/fixtures` and
   `/slips/daily` to confirm the whole pipeline runs, not just that it booted.
   (First request after idle will be slow — free services spin down after 15
   min and take ~1 minute to wake up. That's expected, not a bug.)

## Step 3 — Deploy the frontend to Streamlit Community Cloud

1. share.streamlit.io → **New app** → same GitHub repo → main file path:
   `frontend/streamlit_app.py`.
2. In the app's **Secrets** (Settings → Secrets), add the same settings as a
   TOML block — this is how Streamlit Cloud injects env vars:
   ```toml
   APP_ENV = "production"
   FOOTBALL_PROVIDER = "auto"
   FOOTBALL_PROVIDER_CHAIN = "thesportsdb,api-football,football-data,livescorefootball,sofascore"
   FOOTBALL_PROVIDER_MODE = "fallback"
   THESPORTSDB_API_KEY = "123"
   THESPORTSDB_LEAGUE_ID = "4328"
   API_FOOTBALL_KEY = ""
   FOOTBALL_DATA_API_KEY = ""
   DB_PATH = "postgresql://postgres.PROJECT_REF:PASSWORD@POOLER_HOST:5432/postgres"
   AUTH_JWT_SECRET = "PASTE_A_FRESH_RANDOM_VALUE_HERE"
   RNG_SALT = "PASTE_A_DIFFERENT_FRESH_RANDOM_VALUE_HERE"
   GROQ_API_KEY = ""
   ```

   Replace the two secret placeholders with freshly generated values. Because
   the Streamlit service also imports `Settings`, it must receive valid
   production secrets even though it currently performs login against the
   shared `Store` rather than issuing API bearer tokens.
   **Note on secrets matching:** I checked — `frontend/streamlit_app.py`
   constructs its own `AuthConfig` but never actually uses it to issue or
   verify a token (it handles login with `st.session_state` directly against
   the shared `Store`). So `AUTH_JWT_SECRET`/`RNG_SALT` do **not** need to be
   identical between the two services today. If you later add a feature
   where Streamlit calls the Vercel/Render API with a bearer token, that
   would change — worth a quick re-check of `app/auth.py` usage before
   assuming otherwise then.
3. Deploy. Streamlit Cloud apps also sleep after inactivity on the free tier
   and wake on the next visit — same trade-off as Render's free plan.

## Step 4 — Lock down CORS once both are live

Once you have both URLs, go back to the Render dashboard →
`football-predictor-api` → Environment → set:
```
CORS_ALLOWED_ORIGINS=https://your-app-name.streamlit.app
```
and redeploy. Leaving it at `*` is fine for initial testing only.

## Alternative: both services on Render instead of splitting

If you'd rather keep one provider, add this second service block to
`render.yaml` (Streamlit runs fine as a normal persistent Render process —
this was never a Streamlit-on-Render problem, only a Streamlit-on-Vercel
one):
```yaml
  - type: web
    name: football-predictor-frontend
    runtime: python
    plan: free
    buildCommand: "pip install -r requirements.txt"
    startCommand: "streamlit run frontend/streamlit_app.py --server.port $PORT --server.address 0.0.0.0"
    envVars:
      - key: DB_PATH
        sync: false   # same Postgres URL as the API service
      - key: FOOTBALL_PROVIDER
        value: auto
```
Trade-off: both services now share your workspace's 750 free instance-hours,
so under heavier use you'll hit that ceiling sooner than with the split setup.
